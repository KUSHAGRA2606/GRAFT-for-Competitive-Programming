1. The Core Problem

When building an AI assistant for Competitive Programming (CP) and complex Data Structures, I realized traditional Vector RAG wasn't enough.

Why Standard RAG Fails

  • The Multi-Hop Reasoning Deficit: CP problems require connecting disjoint pieces of logic (e.g., combining Segment Trees with Lazy Propagation). Standard RAG fails to connect these scattered concepts, fetching contexts based on direct keyword similarity rather than a logical path.
  • Global Summarization Bottleneck: When I asked the system broad "sensemaking" questions (e.g., "What are the core paradigms of dynamic programming?"), Vector RAG broke down. You can't fit a whole corpus of algorithms into a context window, and picking the top-$k$ chunks misses the broader thematic patterns.

2. Phase 1: Building a GraphRAG Index

To solve the global sensemaking limitation, my approach was to abandon flat text chunks and build a Knowledge Graph Index directly out of my competitive programming corpus (scraped from Codeforces and CP-Algorithms).

  • Extraction (pipeline/phase1 & phase2): I utilized an LLM to read through the CP documents and extract explicit entities (e.g., "Dijkstra", "Graph"), relationships, and specific algorithmic claims.
  • Community Detection: To make the massive graph scalable, I applied the Leiden Algorithm to mathematically partition it into hierarchical, readable communities of tightly-knit algorithmic concepts.
  • Indexing: Finally, I had the LLM generate a report-like summary for every identified community. This gave me a pre-computed index that completely mapped the global structure.

3. Phase 2: Alignment via RAFT

Having a structured graph wasn't enough; retrievers still fetch noisy blocks of text. I needed to train my model to act like it was taking an "open-book exam" where some pages were deliberately misleading. For this, I implemented RAFT (Retrieval-Augmented Fine-Tuning).

My Training Architecture

In pipeline/phase3, I altered the fine-tuning dataset using a hyperparameter $P\%$:

  • In $P\%$ of instances: I presented the model with an algorithmic Question ($Q$), Golden documents ($D^*$), and completely irrelevant Distractor documents ($D_{i}$).
  • In $(1-P)\%$ of instances: I presented the model with the Question ($Q$) and only Distractor documents ($D_{i}$), forcing it to rely on its parametric memory.
$$ \text{With Context:} \quad Q + D^* + D_1 + \dots + D_k \rightarrow A^* $$
$$ \text{Without Context:} \quad Q + D_1 + \dots + D_k \rightarrow A^* $$

This dual optimization forced my Qwen2.5-3B model to explicitly learn how to ignore misleading distractors while adhering to a structured Chain-of-Thought (CoT) formatting to cite verbatim where it found the answer.

4. Final Implementation Architecture

Unifying approaches across offline fine-tuning and an online inference engine built entirely locally:

[Offline Phase: The Pipeline]
  • Scrape CP-Algorithms / Codeforces (pipeline/phase1)
  • Build Graph & Leiden Summaries (pipeline/phase2)
  • Generate RAFT Dataset (pipeline/phase3)
  • Fine-Tune Qwen2.5-3B using 4-bit QLoRA
[Online Phase: The Agent]
  • UI: User submits a query via Streamlit (src/app.py).
  • Orchestrator: Embeds query and searches FAISS of Community Summaries.
  • Rerank: CrossEncoder reranks top community sentences.
  • Generate: Dense context is injected into the fine-tuned model for response.

5. Hardware Constraints & Local Execution

Ensuring this complex pipeline could run entirely locally without relying on expensive cloud GPUs:

  • 4-Bit Quantization: The base model (Qwen2.5-3B-Instruct) is loaded in 4-bit using BitsAndBytes (nf4 format) to drastically reduce VRAM/RAM footprint.
  • LoRA Adapters: RAFT alignment was done via Low-Rank Adaptation (Rank 16). Lightweight adapters are dynamically loaded on top of quantized base model.
  • CPU-Bound Reranking: CrossEncoder reranker is strictly configured to run on the CPU to prevent OOM errors alongside the LLM.

The result is a fully autonomous, offline AI assistant that parses complex algorithmic paths locally.
