My GRAFT Framework

Graph Retrieval-Augmented Fine-Tuning for Competitive Programming

1. The Core Problem I Set Out to Solve

When building an AI assistant for Competitive Programming (CP) and complex Data Structures, I realized traditional Vector RAG wasn't enough. While standard RAG uses text embeddings to fetch isolated facts, it completely struggles with algorithmic problems due to two main vulnerabilities:


  • The Multi-Hop Reasoning Deficit: CP problems require connecting disjoint pieces of logic (e.g., combining Segment Trees with Lazy Propagation). Standard RAG fails to connect these scattered concepts, fetching contexts based on direct keyword similarity rather than a logical path.

  • Global Summarization Bottleneck: When I asked the system broad "sensemaking" questions (e.g., "What are the core paradigms of dynamic programming?"), Vector RAG broke down. You can't fit a whole corpus of algorithms into a context window, and picking the top-$k$ chunks misses the broader thematic patterns.

2. My Approach Phase 1: Building a GraphRAG Index

To solve the global sensemaking limitation, my approach was to abandon flat text chunks and build a Knowledge Graph Index directly out of my competitive programming corpus (scraped from Codeforces and CP-Algorithms).


  • Extraction (pipeline/phase1 & phase2): I utilized an LLM to read through the CP documents and extract explicit entities (e.g., "Dijkstra", "Graph"), relationships, and specific algorithmic claims.

  • Community Detection: A massive knowledge graph of algorithms becomes a tangled hairball. To make it scalable, I applied the Leiden Algorithm to mathematically partition the graph into hierarchical, readable communities of tightly-knit algorithmic concepts.

  • Indexing: Finally, I had the LLM generate a report-like summary for every identified community. This gave me a pre-computed index that completely mapped the global structure of the algorithmic data.

3. My Approach Phase 2: Alignment via RAFT

Having a structured graph wasn't enough; retrievers still fetch noisy blocks of text. I needed to train my model to act like it was taking an "open-book exam" where some pages were deliberately misleading. For this, I implemented RAFT (Retrieval-Augmented Fine-Tuning).


My Training Architecture

In pipeline/phase3, I altered the fine-tuning dataset using a hyperparameter $P\%$. Here is exactly how I formulated the training mixture:


  • In $P\%$ of instances: I presented the model with an algorithmic Question ($Q$), the Golden/Oracle documents containing the answer ($D^*$), and completely irrelevant Distractor documents ($D_{i}$).

  • In $(1-P)\%$ of instances: I presented the model with the Question ($Q$) and only Distractor documents ($D_{i}$), forcing it to rely on its parametric memory.
$$ \text{With Context:} \quad Q + D^* + D_1 + \dots + D_k \rightarrow A^* $$
$$ \text{Without Context:} \quad Q + D_1 + \dots + D_k \rightarrow A^* $$

This dual optimization forced my Qwen2.5-3B model to explicitly learn how to ignore misleading distractors. Furthermore, I enforced a structured Chain-of-Thought (CoT) formatting, requiring the model to cite verbatim exactly where it found the answer.

4. The Final GRAFT Implementation Architecture

My complete solution, GRAFT, unifies these two approaches across offline fine-tuning and an online inference engine built entirely locally for a CPU-only laptop:

[Offline Phase: The Pipeline]

1. Scrape CP-Algorithms / Codeforces (pipeline/phase1)
2. Build Graph & Leiden Summaries (pipeline/phase2)
3. Generate RAFT Dataset (pipeline/phase3/ & RAFT/)
4. Fine-Tune Qwen2.5-3B using 4-bit QLoRA
[Online Phase: The Agent]

1. src/app.py: The user submits a query via the Streamlit UI.
2. src/graft_agent.py: The LangGraph orchestrator computes the embedding of the query and searches the FAISS database of Leiden Community Summaries.
3. A CrossEncoder reranks the top community sentences.
4. The dense context is injected into the fine-tuned model to generate a fluent, globally-aware response.
